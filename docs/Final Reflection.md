## 1. Project Growth & Evolution
When I started this project, the RPG felt much more like a collection of mechanics living side by side than a cohesive, modular program. Over the course of development, it evolved from a single-threaded, monolithic console loop into a structured C++ project organized across dedicated classes like `Game`, `Player`, `Enemy`, `WeaponSkillManager`, `CombatMenuManager`, `GameInput`, and `PlayerSaveManager`. The biggest improvements came in combat stability, input handling, and data persistence—moving from quick prototypes that could break on unexpected inputs or high stat scaling to a game loop that handles errors cleanly. The single change with the biggest impact on the final project was splitting oversized files and responsibilities into focused manager classes, because it made every later feature and bug fix much easier to add without accidentally breaking unrelated parts of the game.

## 2. Refactoring & Code Quality
One of the biggest areas I refactored was separating weapon skills and combat menu logic out of larger game/player files into `WeaponSkillManager` and `CombatMenuManager`, along with centralizing menu and numeric input inside `GameInput`. Earlier versions had logic tangled together across files, which made tracking state changes harder and occasionally triggered access or build issues—such as `C2248` private-member access errors when `WeaponSkillManager` needed access to `Player` stats, or `C2084` duplicate function definitions in `Player.cpp` after merging branches. Moving responsibilities into clearer boundaries made the codebase much easier to read, maintain, and expand. If I worked on the project again, I would define clean public getters/setters or helper interfaces on `Player` from the start instead of wiring cross-class stat access late in the refactor.

## 3. Features & File I/O
The feature I am most proud of implementing is the dual-weapon combat and skill system paired with boundary-checked damage and resource handling—swapping weapons mid-fight, using abilities, and clamping values so high stat scaling wouldn't corrupt health bars. The most difficult part to integrate was tying new combat states and skills cleanly into existing turn flow without leaving dead toggles or broken resource checks. For persistence, `PlayerSaveManager` saves and loads core character progression—such as stats, health/resource pools, gold, equipped gear, inventory items, and encounter progress—to a local save file. Building file I/O taught me that saving and loading isn't just writing numbers to disk; it requires careful ordering, clear state restoration, and safe handling when a save file is missing or incomplete so old session data doesn't poison a new run.

## 4. Debugging, Challenges & Problem Solving
Throughout development, I ran into plenty of real-world and technologic mishaps. invalid keyboard inputs crashing or stalling menus, private access errors, duplicate definitions after pulling merged changes into `main`, missing skill effects, and integer overflow during heavy attacks. One of the hardest problems to track down was the integer overflow and health-bar wrap-around on high-scaling heavy attacks, where a single strike looked like it inflated the boss's HP into the hundreds of thousands before dropping it on the next hit. At first, I looked at the display and combat flow thinking the UI or turn order was misreporting damage, which didn't explain why the numbers behaved erratically at high stats. Tracing the actual math step-by-step through `Player::PerformHeavyAttack` and `Enemy::TakeDamage` showed that signed integer overflow and unchecked bounds were causing the wrap-around. Clamping damage and health boundaries fixed the root cause, and if I hit a similar bug again, I would inspect raw variable values and math bounds earlier before suspecting UI or flow code.

## 5. Developer Growth
Working on this project over multiple weeks improved my practical C++ skills far more than isolated exercises ever could—especially around class structure, pointer/memory awareness, file I/O, and diagnosing compiler and runtime errors. My habits also shifted: instead of rushing straight into new features or cramming everything into one place, I got much better at tracing call sequences, testing edge cases like non-numeric inputs and low resources, and keeping changes organized through branches, pull requests, and documentation. I still want to improve at catching architectural bottlenecks earlier and pacing work steadily rather than doing heavy catch-up sprints in a single stretch. Developing across multiple weeks showed me that software rarely comes together cleanly on the first pass, and my confidence now comes from knowing I can read an error, trace where state went wrong, and methodically fix it instead of guessing.

## 6. Looking Ahead
If I had another month on this project, I would focus on polish, stress-testing, and deeper save handling. I would add an automated test suite to run extreme stat values through weapon and difficulty damage formulas automatically, expand `PlayerSaveManager` to support multiple save slots along with validation checks for partially corrupted files, and refactor any remaining long functions in `Game`, `Player`, or combat flow into smaller, self-contained helpers. I would also tighten up remaining edge cases around stacked status effects and malformed save edits so the project feels rock-solid from start to finish.
